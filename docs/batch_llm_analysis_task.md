# Задание на анализ пакетной обработки LLM

## Важно

На данном этапе ничего не кодируй и не изменяй.

Не редактируй код, конфигурацию, промпты, тесты и документацию.
Не создавай и не удаляй файлы.
Только изучи проект и подготовь план изменений.
После отчёта остановись и жди отдельного подтверждения.

## Цель

Сейчас каждая статья отправляется в OpenAI отдельным запросом:

1 статья -> 1 вызов модели

Нужно спроектировать переход к пакетной обработке:

до 20 статей -> 1 вызов модели

Пример:

68 статей -> 4 запроса: 20 + 20 + 20 + 8

Общий бизнес-процесс не менять:

RSS -> SQLite -> LLM -> REJECTED или READY -> Telegram -> PUBLISHED

Не менять:

- схему SQLite;
- дедупликацию;
- статусы NEW, REJECTED, READY, PUBLISHED, ERROR;
- обработку RSS;
- правила публикации в Telegram;
- лимит публикаций за запуск.

## Предлагаемая конфигурация

```yaml
llm:
  max_articles_per_run: 100
  batch_size: 20
```

- max_articles_per_run — общее число NEW-статей за запуск;
- batch_size — число статей в одном запросе;
- значение по умолчанию — 20;
- при batch_size: 1 сохраняется текущий одиночный режим.

## Пакетный вход

Каждая статья должна содержать стабильный Article-ID из SQLite:

```text
### ARTICLE

Article-ID: <article_id>
Source: <source_name>
URL: <canonical_url>
Published: <published_at_or_dash>

Title:
<title_or_dash>

Content:
<content_or_dash>

### END ARTICLE
```

Доменный промпт передаётся один раз на весь пакет.

## Пакетный ответ

Для отклонённой статьи:

```text
### RESULT

Article-ID: <article_id>
Status: REJECT

Reason:
<краткое объяснение>

### END RESULT
```

Для принятой статьи:

```text
### RESULT

Article-ID: <article_id>
Status: READY_TO_PUBLISH

Title:
<готовый заголовок>

Text:
<готовый текст>

### END RESULT
```

Правила:

- один результат для каждой входной статьи;
- сопоставление только по Article-ID, а не по порядку;
- результаты могут идти в любом порядке;
- JSON и Markdown code fences запрещены;
- неизвестные Article-ID игнорируются и логируются;
- повторяющийся ID считается ошибкой соответствующей статьи;
- для READY_TO_PUBLISH обязательны непустые Title и Text.

## Обработка ошибок

Не делать повторных одиночных запросов.

Каждый результат пакета обрабатывать независимо.

- Корректный результат сохранить как REJECTED или READY.
- Если результат статьи отсутствует, повреждён, повторяется, имеет неверный статус или не содержит обязательных полей — только эту статью перевести в ERROR.
- Ошибка одной статьи не должна отменять корректные результаты остальных.
- Если весь HTTP-запрос завершился ошибкой — все статьи только этого пакета перевести в ERROR.
- Если ответ не содержит ни одного распознаваемого результата — все статьи пакета перевести в ERROR.
- Существующую одиночную реализацию сохранить только для batch_size = 1, но не использовать как fallback.

Рекомендуемые значения:

- last_error_stage = LLM_BATCH_REQUEST для ошибки запроса;
- last_error_stage = LLM_BATCH_PARSE для ошибки разбора.
